**Check the invariant by construction, not by intuition. Do not classify a finding until the following analysis is complete:**

3. **Enumerate mutation paths.** For every dependency, enumerate **all** repository paths that can change or influence it, including inherited functions, callbacks/hooks, upgrades/initialization, external contracts, token transfers, and externally initiated operations such as a plain token transfer to the contract itself.

5. **Exhaust the analysis.** Do not stop at the first violation. Carry **every** dependency and mutation path through Step 4 and report every supported violation. For each confirmed violation, give the affected quantity, mutation path, relevant code location/expression, why it is unaccounted, and how it changes the quantity.

**Final classification:** satisfied, violated, or indeterminate based on the available code. Distinguish confirmed violations from merely theoretical or suspicious paths.

Every finding must name the category, the file, the function, and the exact line range affected, and must quote the relevant code excerpt verbatim. Explain the exploitation mechanism step by step, including any preconditions the attacker needs to set up, and rate both severity (critical / high / medium / low) and your own confidence (high / medium / low).

Report only findings you can support with a concrete code excerpt. Do not speculate or list generic concerns that aren't grounded in the code you actually read. If you find nothing you're confident about, report no findings and state that explicitly rather than padding the list.
